## 6. Seed-user focus

### Primary seed user

A crypto-active individual with a complex or unresolved wallet history who can provide a public wallet address or permission-safe/redacted transaction data and wants an evidence-backed explanation of what happened and what remains unsupported.

Strong qualification signals:

- multiple wallets or chains;
- DeFi, bridges, staking, swaps, NFTs, agent payments, or wallet-to-wallet transfers;
- prior use of Koinly/CoinTracker/exchange exports with unexplained or misclassified activity;
- tax-return review, historical cleanup, or unresolved reporting concern;
- willingness to review Triage's output for usefulness, clarity, trust, and willingness to pay.

### Secondary seed user

Crypto-focused CPA, bookkeeper, enrolled agent, or tax preparer who manually reviews complicated crypto histories and can evaluate accuracy, evidence quality, workflow fit, time savings, and whether the workpaper is reviewable.

During the bootcamp, professionals are primarily expert reviewers/design partners rather than enterprise procurement targets.

## 7. Evidence vocabulary

Use these words precisely:

- **Submitted** — operator confirmed it was sent to the Growth Partner.
- **Recorded** — repository/local notes contain the claim.
- **User-attested** — operator or user directly stated it, but independent evidence has not been inspected.
- **Verified** — supported by a dated artifact such as a dashboard, public URL, transaction, report, form, screenshot, or system response.
- **Unverified** — no supporting artifact has been found.
- **Target** — intended result; never report it as achieved.

For technical integration also use the status vocabulary from `OPERATING_CONTEXT.md`: `DOCUMENTED`, `MOCK VERIFIED`, `TESTNET VERIFIED`, `PRODUCTION VERIFIED`, `BLOCKED`.

## 8. Technical-quality golden path

Technical Quality is the largest prize component. Preserve and demonstrate this sequence cleanly:

1. Accept a permission-safe public wallet/case.
2. Validate address/network and scope.
3. Retrieve public on-chain activity read-only.
4. Build a chronological ledger.
5. Cite transaction-level evidence.
6. Match supported self-transfers/bridge legs when enough data exists.
7. Classify supported activity.
8. Mark unsupported details `UNRECONCILED` with exact missing evidence.
9. Produce a clear draft for user review.
10. Capture user corrections/confirmation.
11. Freeze/version the report.
12. Verify payment only when the report is a paid pilot.
13. Generate the structured workpaper/PDF.
14. Preserve report hash/provenance status honestly.
15. Deliver the correct report and retain sanitized proof.

Failure paths worth showing/testing:

- invalid wallet;
- unsupported chain;
- explorer/RPC failure;
- missing historical price data;
- missing off-chain records;
- one-sided transfer/bridge leg;
- incorrect or duplicate payment proof;
- payment mismatch/replay;
- PDF generation failure;
- Telegram delivery failure;
- new information requiring versioned correction.

## 13. Final-report integrity rule

Every meaningful final-submission claim must map to an artifact.

Do not write:

- "we had X users" without a defensible count;
- "x402 is integrated" when only metadata or mock code exists;
- "payment succeeded" from a screenshot or user-supplied hash;
- "Agent ID 81 did X" using Agent 14 evidence;
- "cost basis reconstructed" where the supporting acquisition evidence is missing;
- "professional validated" from generic praise that did not include report review.

If the evidence is incomplete, say exactly what is verified and what remains unverified.
